# V0.3：低频随机待机互动

## 使用行为

- 在模型加载完成后，随机等待 45–100 秒，再选择一次待机互动。
- 约 80% 概率显示短暂的脸红或开心眼，约 20% 概率抚胸后回位。连续两次不会都是抚胸，自动表情也避免与上次相同，因此实际动作占比不会高于约 20%。
- 自动表情约 2 秒后恢复；手势沿用已验证的抚胸/停留/回位流程。
- 在桌宠窗口内移动鼠标、按下鼠标、点击、取消操作、失焦，都会重新计时。鼠标在桌面其他区域移动仅用于视线跟随，不会持续推迟待机。
- 按下鼠标时立即中止正在进行的自动互动。手动点击仍按原规则触发表情或手势，自动互动不会消耗手动表情切换顺序。
- 按住鼠标、拖动、手动表情/动作尚未结束时，不启动自动互动，也不排队。
- 菜单打开、窗口隐藏/最小化、网页不可见时暂停。重新显示或长时间没有渲染帧后，重新等待一个随机间隔，不补播遗漏事件。

## 实现边界

`frontend/src/idle.ts` 只管理低频截止时间，不创建后台定时器队列。`interactions.ts` 管理动作与表情的来源，手动操作可以撤销自动动作并恢复其拥有的姿势参数。使用动作序号防止被撤销的动作回调干扰后续手动动作。

`app/bridge.py` 发送窗口及菜单暂停状态。页面自身的可见性也参与暂停判定；仅失去焦点不会永久停用桌宠待机。

检查抢占流程时发现，单独的 requestAnimationFrame 回调无法可靠保证点击命中读取的是刚刚绘制的 WebGL 帧。现在诊断与互动检查放在官方示例绘制完成的回调中执行，避免自动动作被取消后吞掉同一次点击。该修改由资源准备脚本生成，可重复构建。

## 验证

`tools/verify_idle.py` 使用真实 Chrome 和真实模型渲染，借助 Playwright 加速时钟验证等待规则；测试中固定随机源以覆盖表情和动作分支，不改变生产环境的 45–100 秒间隔。渲染截图保留在 `.local/evidence/idle/`。

9 组验收场景：

1. 初始 40 秒内没有自动互动。
2. 自动表情实际显示，不消耗手动表情顺序。
3. 自动表情到时恢复。
4. 自动抚胸实际显示，触发间隔不低于 45 秒。
5. 点击立即抢占自动动作，并正常显示手动表情。
6. 长按和拖动超过多个待机周期仍不触发自动互动，也不排队点击。
7. 手动动作抢占自动表情，并正常回位。
8. 长时间渲染间隔后不立即补播。
9. 重新等待后，自动互动能够恢复。

原有 `tools/verify_interactions.py` 的 7 组鼠标跟随与点击交互回归也通过。Windows `tools/verify_desktop.py` 另外验证真实窗口隐藏/显示、菜单暂停状态、全局视线、点击、拖动、透明合成和退出。

关键证据：`idle-blush.png`、`idle-gesture.png`、`manual-click-preempts-idle.png`、`drag-pauses-idle.png`、`resume-no-burst.png` 和 `result.json`。最终网页及 SDK 错误为 0。

尚未进行长时间真实等待的频率统计，或其他电脑、多屏混合缩放环境的验收。当前没有待机频率设置界面。
